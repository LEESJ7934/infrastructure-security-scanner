## 도출한 7가지 기준

1. **경험:** 문제·범위·기여·판단·결과·한계를 이어 설명한다. 초기 팀 개발과 후속 개선을 구별한다.
2. **기술 증명:** 특정 커밋, 실제 실행 환경, 검사 입력·상태, 증적·테스트·보고서를 연결한다. 단위 테스트 숫자는 운영 검증을 대신하지 않는다.
3. **모의진단 증명:** 자산과 흐름에서 통제를 선택하고, GAP→위험→대책→증적→재평가를 대표 사례로 보여준다. 공식 심사나 경영진 승인으로 확대하지 않는다.
4. **빠른 이해:** 노션 상단에 프로젝트의 역할·핵심 판단·산출물 링크, 세부 명령은 GitHub 문서에 둔다.
5. **이미지:** 한 화면에 하나의 중요한 판단을 담고 대상·시점·환경·결과·한계를 캡션에 적는다. 중복 표보다 정상/오류·전후·원본/해시의 차이가 보이는 증거를 우선한다.
6. **과장 금지:** “인증심사 수행”, “CVE 확정”, “완전 안전”, “위험 100% 제거”, “AWS 조치 완료”, “모든 항목 검증 완료”는 해당 근거 없이 쓰지 않는다.
7. **면접 질문:** 왜 21개인가, GOOD이 아닌 PARTIAL인 이유, L×I 점수 근거, 기능과 운영의 차이, 배너 오탐, FTP와 CVE 관계, EPSS 의미, SHA-256 한계, 다른 앱 비교와 동일 서비스 재점검 차이를 설명할 수 있어야 한다.
