# KISA 2026 주요정보통신기반시설 진단 — 신입 인프라 포트폴리오 우선 범위

## 출처 및 범위
- 사용자가 제공한 **2026 주요정보통신기반시설 기술적 취약점 분석·평가방법 상세가이드**, 총 873쪽. 표지 2026, 배포 게시 시점 2025-12-24.
- 원문 파일명: `주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드.pdf` (GitHub 저장소에 PDF를 복제하지 않음).
- **공식 KISA 기술진단 가이드**와 ISMS-P 인증기준은 별개. KISA 가이드 2쪽은 항목별 판단 기준을 *일반적인 권고*로 설명하며 OS/제품 버전과 기관 운영정책에 따라 최종 판단을 검토하도록 한다.
- 실무 참고: 2025년 하나은행 전자금융기반시설 취약점 분석·평가 RFP는 서버·DBMS·네트워크 장비·정보보호장비 점검, Excel 상세표, Word 요약보고, 개선방안·이행점검을 요구한다. 이 사례는 전국 수행 빈도 통계가 아니다.
- 포트폴리오 우선순위: Unix/Windows/웹 서비스/DBMS > 네트워크·보안장비 > 클라우드. Web Application(웹 보안 진단)은 별도 주제. 제어시스템·PC·이동통신·ESXi 가상화는 현재 별도 전문 LAB이 없어 무리하게 확대하지 않는다.

## 1. 기존 프로젝트 현재 상태
- 원본 `main`은 KISA 일치율을 표시하지 않으며 대부분 `LINUX-LAB-*`, `WIN-LAB-*`, `WEB-LAB-*`, `WAS-LAB-*`, `NET-LAB-*`, `FW-*`, `AWS-LAB-*` 등 **내부 실습 기준**이다.
- 이전 Draft PR #4 기반으로 시작한다. 격리 GitHub Actions Linux Replay에서는 KISA **U-18 PASS**(새 0400 수집), Windows Server 2022 별도 실습에서는 **W-04, W-08 PASS**(5회, 60/60분 적용·재수집)까지 확인했다.
- `README.md`, `docs/portfolio-evidence-mapping.md`, `docs/phase2-final-integration.md`의 한계·수동/자동 출처 설명, 모든 과거 before/after 기록을 보존한다.
- 현재 AWS의 `CT-01` FAIL, `IAM-03` 검토 필요, OPNsense FW-04/05 검토 필요, Windows 감사 항목 검토 필요, 물리 Switch/VTY·실제 VLAN 미검증은 숨기지 않는다.
- 실제 고객사 취약점 진단·인증을 수행한 것으로 기술하지 않는다.

## 3. '100%'의 정확한 정의

- 전체 KISA 가이드(12개 분야) 100%가 아니라, **사전에 확정·동결한 대상 자산/제품/버전 + 공식 점검항목 집합의 실제 검증 완료율**만 사용한다.
- 선정 16개를 확정했다면 `PASS=16, FAIL=0, NEEDS_REVIEW=0, ERROR=0, NOT_TESTED=0`이 실측으로 확인될 때에만 '16/16(100%)' 표현 가능.
- 적용 불가(`NOT_APPLICABLE`)는 사전 승인된 제품·기능 부재와 근거가 있을 때만, PASS에 합산 금지. 기준 미검증은 FAIL 또는 NEEDS_REVIEW로 남긴다.
- 합성 Fixture PASS, 단위테스트 PASS, 코드 완성, 문서 기입, 단순 수집 성공은 **실습 실측 PASS가 아니다**.
- 기존 LAB 결과는 기준·시각이 다른 과거 기록. 새 KISA PASS로 덮어쓰지 않으며 `source_lab_id`와 `official_kisa_id`를 모두 기록한다.
- 정책 검토·고객사 판단이 필수인 항목은 조직 활동이 없는 개인 LAB에서는 **LAB의 실제 수행한 운영 점검 기록** 범위만 입증할 수 있다. 경영진 승인·고객사 책임자·정기 운영 실적을 허구로 생성하지 않는다.
- 실제로 접근 가능한 Docker·Windows VM·OPNsense·AWS에 대해서만 실행, 자산 변경은 명시적 LAB 범위·복구·비용 확인. AWS 과금 자원은 별도 확인 없이 신설 금지.
- 면접에는 '공식 KISA 기준을 참고해 선정한 항목을 **개인 격리 LAB에서 개선·재점검했다**'로 설명한다. '주요정보통신기반시설 고객사 진단 수행', '전체 KISA 기준 준수 인증'으로 표기하지 않는다.

## 4. Codex 구현 순서와 산출물

1. `docs/kisa-2026-selection-freeze.md`: 16개 확정 후보의 대상 자산·제품·버전·적용성·공식 PDF 페이지·수집 가능한 경로를 적고 구현 전에 범위를 고정. 불가한 항목은 **이유 및 대체 계획을 먼저** 기록하고 합의 없이 삭제하지 않는다.
2. `rules/kisa-2026-selected.yaml` 또는 JSON: `kisa_id`, `guide_version`, `target_product`, `criterion`, `evidence_required`, `applicability`, `source_lab_ids` 매핑. 잘못된 버전/출처/중복 ID는 ERROR.
3. 기존 `config_audit/` 엔진 활용: 동일한 원시 관찰값을 '내부 LAB 판정'과 'KISA 해당 항목 판정'으로 각각 내보낸다. 코드만 보고 PASS하지 않음.
4. 대상별 격리 LAB 조치: before에서 FAIL, after에서 KISA PASS가 나오도록 **실제 설정**을 개선. 안전한 관리 접속 경로·로그·정상서비스 확인. 원본 증적/이미 사용 중인 컨테이너를 파괴하지 않음.
5. 새 JSON, 선택 범위 결과 요약, 실제 항목별 관찰 증거 파일, 재점검 매핑, 필요 시 Excel/CSV 상세표(가독성 용도, 허위 PASS 금지).
6. 테스트: 임계값 경계, 실측값 누락, 권한 부족, 도메인/GPO·제품 버전, 합성/수동/자동 출처, 실패 조치, 중복/위조 증적, JSON/PDF/CSV 표기 일관성, 기존 테스트 회귀.
7. `docs/kisa-2026-final-scope-result.md`: 선정 16건 각각 증적 파일·측정 시각·검증 환경·담당 주체·해석 한계, PASS/미완료를 분리. 100% 달성 전에는 진행률을 실제대로 표시.
8. 문서·포트폴리오 과장 수정: 메인 README는 선택 범위와 실제 확인 수치를 일치시켜 업데이트. 팀 원본과 개인 후속 확장 구분.

### 안전상 주의
- 운영 자산, 실서버, 비용 발생 AWS 리소스를 자동으로 조치하지 않는다.
- 네트워크/보안장비의 SSH/HTTPS/VTY 변경은 자신의 관리 연결을 끊을 수 있으므로 격리 LAB에서 rollback 후 검증.
- Windows 도메인 GPO 또는 물리 장비를 근거 없이 개인 LAB의 PASS로 대체하지 않는다.
- 실제 로그의 개인정보나 비밀은 Git에 포함하지 않는다.
- 과거 미검증 상태를 조작하거나 단위테스트를 건너뛰어 PASS를 강제하지 않는다.
